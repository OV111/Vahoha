## QUESTION RULES
1. "question" asks the learner to explain or walk through a realistic situation that touches every subtopic of the group. It must be answerable by speaking, without code or a whiteboard.
2. Each follow-up targets ONE subtopic, is answerable in 90 seconds, and asks why or how, never for a definition or a list of names.

## EVIDENCE RULES (most important)
3. "evidence": 1 to 3 points per subtopic. Each point is ONE idea a correct answer must show, written as a plain statement ("DNS answers are cached for the record's TTL").
4. An idea, never a word: a learner who explains it in everyday words must be able to meet it. Never write "mentions X" or "uses the term X".
5. Checkable from speech: the judge must be able to quote the learner's words as proof.
6. Fair for this layer's level: no expert details a learner at this stage would not have.
7. Not fuzzy: never "understands X" or "knows about X".
8. "notEnough": 1 or 2 answers that sound right but do not count, usually naming the terms without explaining them.
9. "misconceptions": 0 to 2 real wrong beliefs learners hold about this subtopic, each as "Says ..." (what the learner would state). Only ones you are sure are wrong.

## ID RULES
10. Every "id" is lowercase-with-dashes, at most 48 characters. A criterion id is unique within the layer. Evidence and misconception ids are unique within their criterion.
11. Escape quotes so the JSON parses. No trailing commas, no comments.

### Layer 1 of 10: id t3-1
Title: TypeScript and Modern JavaScript Foundations
Group: "TypeScript's type system: structural typing and inference"
  - Subtopic: "Structural typing: assignability is based on shape, not name"
    TypeScript checks whether an object has the required properties, not whether it was declared as a specific type. This means an object literal with the right fields satisfies an interface even without an explicit declaration.
  - Subtopic: "Discriminated unions and exhaustive type narrowing"
    A discriminated union uses a shared literal field (kind: 'success' | 'error') to let TypeScript narrow to the right variant in each branch. Combined with never in a default case, the compiler catches missing branches.
Group: "Generics, utility types, and async patterns"
  - Subtopic: "Generic functions and the extends constraint"
    Generics let you write one function that works with many types. The extends keyword constrains what types are accepted: function getField<T extends { id: number }>(obj: T) guarantees T has an id.
  - Subtopic: "Async/await, Promise types, and error handling with unknown"
    Async functions return Promise<T>. In TypeScript 4+, catch clause errors are typed as unknown rather than any, forcing you to narrow before using them. Use instanceof Error before accessing .message.
Group: "TypeScript tooling and tsconfig for a T3 project"
  - Subtopic: "Key tsconfig options: strict, moduleResolution, and paths"
    strict enables all strictness flags including strictNullChecks. moduleResolution: bundler matches how Vite/Next resolve imports. paths aliases like @/* to src/* remove relative import chains.
  - Subtopic: "Utility types: Partial, Omit, Pick, and ReturnType in practice"
    Partial<User> makes all fields optional for update DTOs. Omit<User, 'passwordHash'> creates a safe public user type. ReturnType<typeof myFn> extracts a function's return type without repeating it.
Group: "Modern JavaScript patterns used throughout T3"
  - Subtopic: "ES modules, destructuring, and optional chaining"
    T3 uses ESM throughout. Destructuring extracts props cleanly in components; optional chaining (user?.profile?.avatar) prevents null reference errors when traversing nested objects from API responses.
  - Subtopic: "Node.js module system and package.json type field"
    Setting type: module in package.json makes .js files use ESM. The T3 stack uses this with .ts extensions and tsx for JSX. Understanding module resolution prevents import errors at build time.

### Layer 2 of 10: id t3-2
Title: React Fundamentals
Group: "React's rendering model and the component lifecycle"
  - Subtopic: "How React reconciles the virtual DOM and batches renders"
    React builds a virtual DOM, diffs it against the previous tree, and applies minimal DOM mutations. React 18 batches all state updates by default — even inside timeouts and native event handlers.
  - Subtopic: "Hooks rules: why they can't be called conditionally"
    React tracks hooks by call order on each render. Calling a hook inside an if-block would change the count between renders, corrupting the internal state array. The linter rule enforces this at dev time.
Group: "TypeScript integration with React components and hooks"
  - Subtopic: "Typing component props with interfaces and React.FC"
    Define a props interface and annotate the component: function Card({ title }: CardProps). Avoid React.FC — it hides the return type and makes component typing less explicit.
  - Subtopic: "Typing useState, useRef, and event handlers"
    useState<User | null>(null) explicitly types nullable state. useRef<HTMLInputElement>(null) types the ref target. Event handlers use React.ChangeEvent<HTMLInputElement> for the event type.
Group: "Building components with hooks and controlled forms"
  - Subtopic: "useState and useEffect: state updates, stale closures, and cleanup"
    Calling the setter doesn't change state until the next render. Effects that reference state values in their closure will see stale values unless listed in the dependency array.
  - Subtopic: "Controlled inputs and form handling in TypeScript React"
    A controlled input's value is driven by React state. Type the onChange handler as (e: React.ChangeEvent<HTMLInputElement>) => void and update state with e.target.value.
Group: "List rendering, composition, and prop patterns"
  - Subtopic: "Rendering lists with stable key props from entity IDs"
    Keys help React identify which items changed, added, or removed. Use entity IDs from the database, not array indices. Index-based keys break reconciliation when items are reordered.
  - Subtopic: "Component composition with children and render props"
    Pass JSX as the children prop for layout components (Card, Modal, Layout). Render props pass a function as a prop to give the parent control over what gets rendered inside.

### Layer 3 of 10: id t3-3
Title: Next.js App Router
Group: "Next.js App Router rendering model"
  - Subtopic: "Server components versus client components: execution boundary"
    Server components run only on the server — they can access databases and secrets directly but cannot use hooks or browser APIs. 'use client' marks the boundary where code runs in the browser.
  - Subtopic: "Static rendering, dynamic rendering, and streaming with Suspense"
    Static routes are rendered at build time and cached. Dynamic routes opt out of caching (cookies, searchParams). Streaming with Suspense sends the static shell immediately and streams dynamic content as it resolves.
Group: "File-based routing and the layout system"
  - Subtopic: "How layout.tsx, page.tsx, and loading.tsx compose the route tree"
    layout.tsx wraps page.tsx for a route segment. Nested layouts compose without re-mounting parent layouts on navigation. loading.tsx automatically wraps page.tsx in a Suspense boundary.
  - Subtopic: "Data fetching in server components: fetch with cache control"
    In server components, fetch() extends the native API with cache: 'force-cache' (default static), 'no-store' (dynamic), or next: { revalidate: 60 } (ISR). This controls how Next.js caches the response.
Group: "Setting up and navigating a Next.js App Router project"
  - Subtopic: "Dynamic routes with [slug] and catch-all [...slug] segments"
    A file named [id]/page.tsx matches /posts/123 and provides params.id. Catch-all segments [...slug] match any depth. generateStaticParams() pre-generates dynamic routes at build time.
  - Subtopic: "The Link component and useRouter for client-side navigation"
    <Link href='/about'> prefetches the route in the background and navigates without a full page reload. useRouter() from 'next/navigation' (not 'next/router') provides push, replace, and back in App Router.
Group: "Metadata, error boundaries, and loading states"
  - Subtopic: "Generating SEO metadata with the Metadata API"
    Export a metadata object or generateMetadata function from any layout.tsx or page.tsx to set title, description, and Open Graph tags. Dynamic metadata can fetch data server-side.
  - Subtopic: "error.tsx and not-found.tsx for route-level error handling"
    error.tsx must be a client component ('use client') and receives error and reset props. not-found.tsx renders when notFound() is called from a server component. Both scope their UI to the nearest route segment.

### Layer 4 of 10: id t3-4
Title: Styling with Tailwind CSS
Group: "How Tailwind's utility-first model works"
  - Subtopic: "Tailwind purges unused classes at build time via content scanning"
    Tailwind scans files listed in content: [] and removes any class not found in the source. This is why dynamically constructed class strings (bg-${color}-500) won't work — the scanner can't see them.
  - Subtopic: "The cascade in Tailwind: last class wins within the same property"
    Tailwind classes are all single-purpose — each sets one CSS property. When two classes set the same property, the one that appears later in the stylesheet wins, which is determined by Tailwind's generated order, not your JSX order.
Group: "Design tokens and the theme system"
  - Subtopic: "Customizing the theme: colors, spacing, and breakpoints"
    Extend the theme in tailwind.config.ts to add brand colors, custom spacing values, or additional breakpoints. Use extend: {} to add to the defaults rather than replace them entirely.
  - Subtopic: "Dark mode with the class strategy and prefers-color-scheme"
    With darkMode: 'class', add dark: variants that only apply when a dark class is on the html element. Toggle it via JavaScript to implement a manual dark mode toggle independent of the OS setting.
Group: "Tailwind layout and responsive design patterns"
  - Subtopic: "Responsive breakpoints: mobile-first with sm, md, lg, xl prefixes"
    Tailwind is mobile-first — unprefixed classes apply at all sizes. sm:flex applies only at ≥640px. Build layouts for small screens first, then override with prefixed classes for larger viewports.
  - Subtopic: "Flexbox and grid utilities: flex, grid, gap, col-span"
    flex + items-center + justify-between handles most one-dimensional layouts. grid grid-cols-3 gap-4 handles card grids. col-span-2 makes a cell span multiple columns.
Group: "Reusable component patterns with Tailwind in T3"
  - Subtopic: "Using clsx and tailwind-merge to compose conditional classes"
    clsx conditionally joins class strings. tailwind-merge (twMerge) deduplicates conflicting Tailwind classes — combine them in a cn() utility used throughout T3 and shadcn/ui projects.
  - Subtopic: "Applying variants with the group and peer modifiers"
    Add the group class to a parent, then use group-hover:text-white on children to style them on parent hover. peer lets adjacent siblings style each other — useful for checkbox-driven label styles.

### Layer 5 of 10: id t3-5
Title: End-to-End Type Safety with tRPC
Group: "How tRPC eliminates the client-server type boundary"
  - Subtopic: "tRPC's type inference: how server types flow to the client"
    tRPC exports the router's AppRouter type. The client imports it as a type-only import, so there's zero runtime cost. TypeScript infers input and output shapes from the router definition — no code generation needed.
  - Subtopic: "Zod input schemas in tRPC procedures: parsing untrusted input"
    Every tRPC procedure with .input(schema) calls zod.parse() on the incoming data before your resolver runs. Invalid input throws a TRPCError with code BAD_REQUEST, which the client receives as a typed error.
Group: "tRPC middleware and context for auth and request data"
  - Subtopic: "Context: passing the session and database client to procedures"
    tRPC context is created per request (createContext) and injected into every procedure. Put the session and Prisma client in context so any procedure can access them without importing globals.
  - Subtopic: "Protected procedures with tRPC middleware"
    A protectedProcedure wraps the base procedure with middleware that checks ctx.session and throws UNAUTHORIZED if missing. Composing protected procedures ensures auth is never forgotten on a mutation.
Group: "Defining tRPC routers and procedures"
  - Subtopic: "Queries versus mutations: when to use each in tRPC"
    Queries are for reading data (GET semantics); mutations are for writes (POST/PUT/DELETE semantics). TanStack Query treats them differently — queries are cached and refetched; mutations trigger manual invalidation.
  - Subtopic: "Merging routers: splitting tRPC into feature-based sub-routers"
    Create separate routers for posts, users, comments and merge them into the root router. The client accesses them as trpc.posts.list.useQuery() — the nesting mirrors the router structure.
Group: "Using tRPC on the client with TanStack Query"
  - Subtopic: "useQuery and useMutation hooks generated by the tRPC client"
    trpc.post.list.useQuery() returns { data, isLoading, error } with full types. trpc.post.create.useMutation() returns { mutate, isPending }. These are thin wrappers around TanStack Query's hooks.
  - Subtopic: "Cache invalidation after mutations with utils.invalidate()"
    After a mutation, call utils.post.list.invalidate() inside onSuccess to mark that query stale and trigger a background refetch. This keeps the UI consistent without a page reload.

Group: "Prisma's schema-first approach and type generation"
  - Subtopic: "How Prisma generates a typed client from schema.prisma"

  - Subtopic: "Prisma relations: one-to-many and many-to-many in the schema"
    A one-to-many relation adds a foreign key field and a relation field on both models. Many-to-many uses an implicit join table (Prisma manages it) or explicit when the join table has extra fields.
Group: "Prisma migrations and the development workflow"
  - Subtopic: "prisma migrate dev: generating, naming, and applying migrations"
    prisma migrate dev computes the diff between your schema and the database, writes a migration SQL file, applies it, and regenerates the client. Each migration file is committed to source control.
  - Subtopic: "N+1 query problem and how to fix it with Prisma's include"
    Fetching a list of posts and then querying each post's author separately causes N+1 database queries. Prisma's include: { author: true } fetches all authors in a single JOIN query.
Group: "Prisma CRUD operations in tRPC procedures"
  - Subtopic: "findMany with where, orderBy, take, and skip for pagination"
    prisma.post.findMany({ where: { authorId }, orderBy: { createdAt: 'desc' }, take: 10, skip: page * 10 }) is the standard pagination pattern. Cursor-based pagination scales better for large tables.
  - Subtopic: "Prisma transactions for multi-step atomic writes"
    prisma.$transaction([op1, op2]) runs both operations atomically. If either fails, both roll back. Use interactive transactions for conditional logic inside the transaction block.
Group: "Prisma Studio and seeding for development"
  - Subtopic: "Prisma Studio: browsing and editing data visually"
    npx prisma studio opens a web UI to browse tables, filter rows, and edit records. It's invaluable during development for inspecting the database state without writing SQL.
  - Subtopic: "Writing an idempotent seed script with upsert"
    Use prisma.user.upsert({ where: { email }, update: {}, create: {...} }) in seed scripts so they can be run repeatedly without creating duplicate records. Register the script in package.json prisma.seed.

### Layer 8 of 10: id t3-8
Title: Advanced State and Data Fetching
Group: "TanStack Query's cache model and server state semantics"
  - Subtopic: "staleTime, gcTime, and the background refetch lifecycle"
    staleTime determines how long a query result is fresh — during this window, no refetch happens. After staleTime, the cached data is served instantly while a background refetch runs. gcTime controls when unused cache entries are garbage-collected.
  - Subtopic: "Query invalidation versus refetch: when to use each"
    invalidateQueries marks a query stale and triggers a background refetch if the query has active observers. refetchQueries forces an immediate refetch. Prefer invalidation after mutations — it's more surgical.
Group: "Optimistic updates and rollback on error"
  - Subtopic: "Optimistic updates: apply immediately, rollback on mutation failure"
    In onMutate, cancel in-flight queries, snapshot the current cache, and apply the optimistic change. In onError, restore the snapshot. In onSettled, invalidate to sync with the server's truth.
Group: "Advanced TanStack Query patterns in T3"
  - Subtopic: "Infinite queries for cursor-based pagination with fetchNextPage"
    useInfiniteQuery provides fetchNextPage, hasNextPage, and isFetchingNextPage. The getNextPageParam function extracts the cursor from the last page. Intersect an invisible div with IntersectionObserver to trigger load-more.
  - Subtopic: "Prefetching data in server components for instant client hydration"
    Call queryClient.prefetchQuery in a server component and dehydrate the cache with dehydrate(queryClient). Pass it to HydrationBoundary on the client so the initial render has data without a loading state.
Group: "Global state versus server state in T3"
  - Subtopic: "When to use Zustand for client-only global state"
    Use TanStack Query for anything from the server. Use Zustand for UI state that doesn't come from an API: modal open/closed, theme, sidebar expanded. Mixing them for server data leads to stale data bugs.
  - Subtopic: "Mutation lifecycle callbacks: onMutate, onError, onSuccess, onSettled"
    TanStack Query mutations provide four lifecycle callbacks. onMutate runs before the request for optimistic updates. onError receives the error and rollback context. onSettled always runs — use it for final invalidation.
